### 2.3 一个关键的数据问题（已修复）

初版标注中 **长城存在"一图多框"**：78 张图有 104 个框，一张画面里标了 2~3 段不同位置的城墙。
YOLO 对单实例地标学到的是"一图应输出多个框"，直接后果是推理时同一栋建筑被重复检出、且"框得最准的那个"置信度排序反而靠后（见 4.2 节误差分析）。

修复方式：**同一张图只保留一个主框**（覆盖画面中长城主体），把 104 框合并为 78 框。修复后模型的长城指标显著提升（见 4.3 节对比）。

## 3. 训练配置

```
模型      yolo11n.pt（COCO 预训练迁移学习，2,598,023 参数，6.4 GFLOPs @320）
输入      imgsz=320
批大小    batch=16
冻结      freeze=10（冻结 backbone 前 10 层，训练提速约 1/3）
优化器    AdamW（optimizer=auto 自动选择），lr0≈1.1e-3，cos_lr=True
轮数      100 epochs，patience=100（配合余弦退火跑满）
增强      mosaic=1.0（最后 10 轮关闭）、scale=0.5、fliplr=0.5、translate=0.1
缓存      cache='ram'（263 张解码后约 0.1GB）
线程      workers=0（Windows 下避免多进程 dataloader 开销）
```

实测速度：**约 13.0~14.2 秒/epoch**，100 轮 **21.7 分钟**（与开工前预估的 23~34 分钟吻合）。

> 注：训练入口已修正为 `project` 传绝对路径。ultralytics 会把相对 `project` 再拼一层 `settings.runs_dir`，此前 `project="runs/detect"` 实际输出到 `runs/detect/runs/detect/<name>/`。

## 4. 评估结果

### 4.1 最终模型逐类指标

**test 集（34 图 / 36 框）**

| 类别 | P | R | mAP@50 | mAP@50-95 |
|------|---|---|--------|-----------|
| 全部 | 0.891 | 0.861 | **0.869** | **0.532** |
| eiffel_tower | — | — | 0.995 | 0.694 |
| sydney_opera | — | — | 0.815 | 0.504 |
| oriental_pearl | — | — | 0.995 | 0.591 |
| statue_of_liberty | — | — | 0.745 | 0.531 |
| great_wall | — | — | 0.794 | 0.339 |

**val 集（32 图 / 33 框）**

| 类别 | mAP@50 | mAP@50-95 |
|------|--------|-----------|
| 全部 | 0.872 | 0.584 |
| eiffel_tower | 0.995 | 0.758 |
| sydney_opera | 0.995 | 0.660 |
| oriental_pearl | 0.734 | 0.473 |
| statue_of_liberty | 0.944 | 0.661 |
| great_wall | 0.693 | 0.366 |

两个划分的交叉验证结论：

- **eiffel_tower / statue_of_liberty 稳定**（val 与 test 均 ≥0.94，mAP@50-95 0.66~0.76），是最可靠的两类。
- **statue 在 test 上 0.745 是样本波动**：test 只有 4 张自由女神图，一张判错即损失 25 个百分点；同一模型在 val（7 张）上为 0.944。**不应据此判定该类退化**。
- **oriental_pearl 在 val 上 0.734 偏低**（test 0.995），差异来自 val 仅 3 张图（3 个框），单图权重过高。
- **great_wall 是真实短板**：两个划分都最低（0.794 / 0.693），mAP@50-95 仅 0.34~0.37，说明框的贴合度不够，而不只是"找不到"。

### 4.2 长城短板归因（逐图诊断）

对 test 集 11 张长城图逐张比对预测框与 GT：

| 判定 | 数量 | 说明 |
|------|------|------|
| 命中（IoU≥0.5 且 conf≥0.25） | 8 | — |
| 低置信（IoU≥0.5 但对应框 conf<0.25） | 3 | 最高分框不是"框对的那个" |
| 漏检（完全无框） | **0** | — |
| 定位偏差（有框但 IoU<0.5） | 0 | — |

**结论：长城不存在"识别不出"的问题，问题在重复框竞争的排序。** 修复前（多框标注）一张图常输出 2~8 个候选框，正确框的置信度被压到 0.06~0.14；改为单框标注后，同一张图只输出 1 个框、置信度升到 0.50~0.88。

根因是数据层面的：**长城框面积中位数 0.586**（占全图 59%），其他类仅 0.11~0.43，最大框达 91%。在 320px 输入下这类超大目标几乎铺满整图，模型只能看到局部砖石纹理、缺少整体形状约束，定位精度天然吃亏。

### 4.3 两版模型对比（数据修复的价值）

| 指标 | landmark_v1（长城多框 104） | **landmark5_v3_wallfix（长城单框 78）** |
|------|------------------------------|----------------------------------------|
| test mAP@50 | 0.873 | 0.869 |
| test mAP@50-95 | 0.511 | **0.532** |
| val mAP@50 | 0.881 | 0.872 |
| val mAP@50-95 | 0.553 | **0.584** |
| great_wall（test） | 0.637 / 0.245 | **0.794 / 0.339** |
| great_wall（val） | 0.614 / 0.334 | **0.693 / 0.366** |
| 长城实测置信度（演示视频同帧） | 0.39（只框局部） | **0.50（覆盖主体）** |

长城类 mAP@50 提升 **+0.157（test）/ +0.079（val）**，mAP@50-95 提升 **+0.094 / +0.032**；整体 mAP@50 基本持平（-0.004），mAP@50-95 提升 +0.02~0.03。**这是净收益，故最终采用 wallfix 版本。**

> `models/archive_best_landmark_v1_oldlabels.pt` 保留了旧标注训练的权重，供回溯对比。

### 4.4 分辨率消融实验：320 vs 480（谁更强？）

为验证"提高输入分辨率能救长城"这一假设，用完全相同的配置（yolo11n / batch16 / freeze10 / cos_lr / 单框标注）额外训练一版 **imgsz=480、70 epochs**（29.2 分钟，best=epoch 26）。

> 评估口径必须与训练分辨率一致：480 模型按 480 评估，320 模型按 320 评估。若把 480 模型按 320 评估，test mAP50 会虚高到 0.896 而 mAP50-95 虚高到 0.565，是错误对比。

| 指标 | 320 模型 @320（交付版） | 480 模型 @480 | 差异 |
|------|------------------------|---------------|------|
| test mAP@50 | 0.869 | **0.919** | +0.050 |
| test mAP@50-95 | **0.532** | 0.497 | −0.035 |
| val mAP@50 | 0.872 | **0.899** | +0.027 |
| val mAP@50-95 | 0.584 | **0.591** | +0.007 |
| 端到端单图 | **32.7 ms / 30.6 FPS** | 40.6 ms / 24.6 FPS | −20% 速度 |
| 纯前向 | **21.7 ms** | 28.6 ms | +32% |

逐类（test，各自分辨率）：

| 类别 | 320 | 480 |
|------|-----|-----|
| eiffel_tower | 0.995 / 0.694 | 0.995 / 0.508 |
| sydney_opera | 0.815 / 0.504 | 0.815 / 0.531 |
| oriental_pearl | 0.995 / 0.591 | 0.995 / 0.658 |
| statue_of_liberty | 0.745 / 0.531 | **0.995** / 0.429 |
| great_wall | 0.794 / 0.339 | 0.796 / **0.359** |

**结论（不含糊）：**

1. **480 稳定提升的是"检出/粗定位"**：mAP@50 在两个划分上都涨（+0.027 / +0.050），自由女神 test 从 0.745 直接补到 0.995——这正是 320 下"框对了但分数不够"那几张图被救回来的结果。
2. **480 没有提升"框的贴合精度"**：mAP@50-95 在 val 只 +0.007（噪声级），在 test 反而 −0.035。埃菲尔在高 IoU 阈值下明显变差（0.694→0.508），说明大分辨率下框回归反而更"松"。
3. **长城的 mAP@50-95 略有改善**（0.339→0.359 / 0.366→0.392），但 AP50 没动（0.794→0.796）——长城的问题不是分辨率，而是**这类超大目标的定位置信度本身缺乏足够训练样本支撑**（78 张）。
4. **代价只有 −20% 速度**（30.6→24.6 FPS），比理论上 2.25 倍的像素量小得多，因为小模型下 Python 前后处理占比大。

**交付决策：仍以 320 版为 `models/best.pt`**。理由：① 更严格的 mAP@50-95 在 test 上更高（0.532 vs 0.497）；② 速度更快；③ 已有演示、文档、桌面素材全部基于它，一致性更好；④ 480 的 mAP@50 优势建立在 34 张 test 上，置信区间有限。

480 权重保留为 `models/best_480.pt`，作为"高召回模式"备选：

```bash
python src/inference/predict_image.py --source data/demo_imgs/ --weights models/best_480.pt --imgsz 480 --save
```

## 6. 速度基准（CPU）

| 路径 | 单图端到端 | 纯前向 | 预处理 | 后处理 |
|------|-----------|--------|--------|--------|
| PyTorch (`models/best.pt`) | **27.3 ms / 36.6 FPS** | 19.41 ms | 0.92 ms | 0.82 ms |
| OpenVINO (`models/best_openvino_model`) | 27.1 ms / 36.8 FPS | **17.74 ms** | 0.84 ms | 1.01 ms |
| 加速比 | 1.01x | 1.09x | — | — |

**必须纠正早期文档里"OpenVINO 在 CPU 上再快 2~3 倍"的说法**：本任务模型仅 2.6M 参数、输入 320px，端到端瓶颈在 Python 预处理/后处理与调度，不在卷积算子，因此 OpenVINO 只带来约 9% 的前向提速、端到端无可测差异。

OpenVINO 值得用的场景：imgsz≥640、换 yolo11s/m 以上模型、或需批量吞吐（batch>1）。模型已导出备用：`models/best_openvino_model/`（10.2MB），推理时加 `--openvino` 即可切换。

参考：如果后续把 imgsz 提到 640，纯前向约 3.5~4 倍耗时（≈70~80ms/帧，12~14 FPS），届时 OpenVINO 的算子优化收益才明显。

## 7. 已知限制与后续改进

| 问题 | 影响 | 建议 |
|------|------|------|
| test 集仅 34 张，单类最少 3 张 | 单类指标置信区间宽，statue/oriental 的跨集波动即源于此 | 扩到 600+ 张、每类 ≥80 张 |
| 长城框面积中位数 59%，目标过大 | mAP@50-95 仅 0.34，框贴合度不足 | ① ~~提分辨率~~ **已实测 480 无稳定收益**（见 4.4）；② 标注改为"框长城主体走向段"而非整片山体；③ 补该类样本到 150+ 张 |
| 部分图片带站点水印（小红书/知乎） | 存在学到水印纹理的隐患，演示观感差 | 采集阶段即过滤；当前已在 train 侧尽量剔除，test 侧残留几张不影响训练 |
| 单图多目标场景（一张图两栋不同建筑） | 未覆盖，当前每类按单实例建模 | 若需多类共存，补"同图多类"样本重训 |
| `oriental_pearl` 在 val 上偏低 | 3 张样本导致，非模型能力问题 | 补该类数据后重划分 |

### 如果要继续提升精度（按性价比排序）

1. **加数据**：每类补到 100+ 张（尤其 great_wall、oriental_pearl），爬虫脚本 `src/data_prep/collect_images.py` 现成可用。这是唯一能解决"框贴身"问题的方向。
2. ~~**提分辨率**~~ **已验证无效**：480 只提升 mAP@50、不提升 mAP@50-95，代价 −20% 速度，见 4.4 节。若只为"漏检多"的场景可切 `models/best_480.pt`。
3. **解冻训练**：`--freeze 0`，全网络微调，小数据集上易过拟合，需配合更强增强。
4. **换更大模型**：`--model yolo11s --imgsz 416`，CPU 上训练时间约 2.5 倍，精度通常 +0.02~0.04。
