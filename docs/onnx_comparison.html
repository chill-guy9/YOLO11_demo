五个类别 AP@50 全部相同：0.9950 / 0.7816 / 0.9950 / 0.8283 / 0.7423。 网络原始输出 (1,9,2100) 最大绝对误差 9.46e-4、平均 1.55e-5（算子融合与浮点累加顺序造成的舍入级差异）。

避坑：不对齐预处理会测出假精度差。 静态 ONNX 被强制正方形 letterbox (1,3,320,320) / 2100 anchors，而 .pt 默认 rect=True 走矩形 (1,3,320,256) / 1680 anchors。直接对比会得到 0.8221 vs 0.8684； 给 .pt 显式 rect=False 后 P / R / mAP 与 ONNX 逐位相同。小测试集上这种输入差异会被放大成 0.046 的"精度差"。

二、优缺点对照

PyTorch .pt

  • 可继续训练 / 微调，是再导出其它格式的唯一源头
  • 体积小（5.21 MB，FP16 序列化，加载时自动转 FP32）
  • 支持动态尺寸、矩形 letterbox 推理
  • Ultralytics 官方 train / val / plots / benchmark 工具链齐全

短板

  • 部署必须带 PyTorch，环境重、跨语言几乎不可行
  • CPU 端到端比 ONNX 慢约 33%
  • pickle 反序列化安全、torch 版本兼容风险

ONNX Runtime .onnx

  • 精度零损失，检测框与置信度完全一致
  • CPU 提速 1.33×，运行时只需 onnxruntime（几十 MB）
  • 框架中立：C++ / Java / JS / 移动端 / Web，可再转 TensorRT、OpenVINO、INT8
  • 类别名、stride、imgsz 等元数据已写进图，便于独立交付

短板

  • 不能训练；文件约 2 倍大（FP32 落盘）
  • 静态 [1,3,320,320]，换分辨率需重导或 --dynamic
  • 脱离 Ultralytics 需自写预处理 + 解码 + NMS（本项目已提供两套脚本）
  • opset / 算子兼容需在目标设备复验

四、两条纯部署链路（均不依赖 torch / ultralytics）

静态 FP32 版 · 自写 NMS

只依赖 numpy + cv2 + onnxruntime；自己实现 letterbox（含 BGR→RGB）、xywh→xyxy 解码、按类别 NMS、坐标还原。

校验：34 张 test 35/35 框匹配、conf 差 0、坐标差 0.54 px。

python src/inference/predict_onnx_native.py --save
python runs/detect/landmark_v5_1025/compare/verify_native_onnx.py

--nms 入图版 · 免写 NMS

输出直接是 (x1,y1,x2,y2,conf,cls)，只需 conf 过滤 + 坐标还原；端到端 23.65 ms，四变体中最快。

校验：34 张 test 38/38 框匹配、conf 差 0、坐标差 0.52 px。

python src/inference/predict_onnx_nms_native.py --save
python runs/detect/landmark_v5_1025/compare/variants/verify_nms_native.py

两个脚本输出格式不同，不能混用模型。写纯部署脚本最容易漏的是 BGR→RGB 翻转：漏掉会令置信度从 0.917 掉到 0.785、框明显内缩。
